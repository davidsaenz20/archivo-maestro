ARQUITECTURA DE LANDING

1. FUNCIÓN

Este documento define la estructura funcional de una landing SEO local generada a partir de una oportunidad previamente validada.

La landing no se genera directamente desde una combinación de palabras clave.

El flujo obligatorio es:

EVIDENCIAS

↓

OPORTUNIDAD

↓

MOTOR

↓

DECISIÓN CREAR

↓

URL

↓

ARQUITECTURA DE LANDING

↓

BLOQUES

↓

DATOS

↓

IA

↓

VALIDACIÓN

↓

PUBLICACIÓN

---

2. PRINCIPIO FUNDAMENTAL

Una landing debe responder a una intención concreta y aportar información útil, específica y diferenciada.

No debe limitarse a sustituir automáticamente el nombre de una localidad dentro de una plantilla.

La estructura debe poder reutilizarse para cientos o miles de páginas sin convertirlas en copias prácticamente idénticas.

---

3. ENTRADA DE LA LANDING

Una landing solo puede comenzar a construirse cuando existe una oportunidad con decisión:

CREAR

La entrada mínima debe identificar:

- Servicio.
- Subservicio, si existe.
- Localidad.
- Provincia.
- URL.
- Intención principal.
- Evidencias disponibles.
- Información local disponible.
- Datos comerciales autorizados.
- Bloques requeridos.
- Bloques opcionales.
- Restricciones.

Ejemplo conceptual:

servicio = fontanero
subservicio = desatascos
localidad = Marbella
provincia = Málaga
decisión = CREAR
url = /fontanero/desatascos/marbella/

---

4. ESTRUCTURA GLOBAL

La landing tendrá conceptualmente:

1. Header.
2. Navegación.
3. Hero.
4. Contenido principal.
5. Bloques de servicio.
6. Información local.
7. Elementos de confianza.
8. FAQ.
9. CTA.
10. Footer.

Los bloques concretos dependerán del tipo de oportunidad.

---

5. HEADER

El header debe ser coherente en todo el sitio.

Debe poder contener:

- Logo o identidad de marca.
- Menú principal.
- Acceso a servicios.
- Acceso a localidades cuando corresponda.
- Contacto o CTA principal.

El header es un elemento global del sitio y no debe reinventarse para cada municipio.

---

6. MENÚ

El menú debe responder a la arquitectura real del sitio.

No se crearán enlaces a páginas que no existan o no estén validadas.

La generación automática debe comprobar que cada enlace apunta a una URL válida.

La navegación puede incluir:

- Servicios principales.
- Localidades estratégicas.
- Contacto.
- Otros elementos globales.

No todas las localidades generadas deben aparecer automáticamente en el menú principal.

La navegación global debe mantenerse usable aunque existan miles de páginas.

---

7. HERO

El hero identifica inmediatamente:

- Qué servicio se ofrece.
- Dónde se ofrece.
- Qué problema o intención resuelve.
- Qué acción puede realizar el usuario.

Debe contener, cuando proceda:

- H1.
- Subtítulo.
- CTA principal.
- Señales de confianza reales.

Ejemplo conceptual:

H1: Desatascos en Marbella

El texto definitivo será generado utilizando los datos y reglas de contenido.

No se debe introducir información comercial no verificada.

---

8. H1

Cada landing indexable tendrá un único H1 principal.

El H1 debe representar la intención principal de la página.

Debe ser coherente con:

- servicio;
- subservicio;
- localidad;
- intención.

La IA no puede cambiar la intención de la página mediante el H1.

---

9. INTRODUCCIÓN

Después del hero podrá existir una introducción breve que explique:

- qué servicio se ofrece;
- para quién;
- en qué localidad;
- qué necesidad resuelve.

Debe aportar contexto real.

No debe utilizarse para rellenar espacio con texto genérico.

---

10. BLOQUE DE SERVICIO

La landing debe explicar el servicio principal con claridad.

Puede incluir:

- Qué incluye.
- Problemas que resuelve.
- Situaciones habituales.
- Alcance del servicio.
- Limitaciones cuando sean relevantes.

El contenido deberá basarse en información real disponible.

---

11. BLOQUES DE SUBSERVICIOS

Cuando la oportunidad corresponda a un subservicio, este debe ocupar un lugar central.

Ejemplo:

"fontanero + desatascos + Marbella"

La página debe explicar el servicio de desatascos, no generar una landing genérica de fontanería cambiando únicamente el título.

---

12. PROBLEMAS / NECESIDADES

Cuando sea relevante, la landing puede organizar información alrededor de problemas reales del usuario.

Ejemplos para fontanería:

- atasco;
- fuga;
- falta de agua caliente;
- avería;
- rotura;
- instalación.

Los problemas incluidos deben guardar relación con la intención de la página.

---

13. INFORMACIÓN LOCAL

Una landing local debe incorporar información específica cuando exista evidencia suficiente.

Puede incluir:

- zonas atendidas;
- barrios;
- urbanizaciones;
- características del municipio;
- tipos de vivienda;
- necesidades locales;
- contexto turístico;
- segundas residencias;
- características del cliente;
- cobertura real.

No se deben inventar características locales.

Si no existe información suficiente, el sistema debe reducir el contenido local antes que inventarlo.

---

14. COBERTURA

Puede existir un bloque de cobertura territorial.

Debe utilizar únicamente localidades, barrios o zonas realmente atendidos o cuya relación esté documentalmente justificada.

No debe generarse una lista masiva de lugares solo para aumentar relevancia semántica.

---

15. PROCESO DE TRABAJO

Cuando sea útil para la intención, la landing puede explicar el proceso:

1. Contacto.
2. Evaluación inicial.
3. Desplazamiento o actuación.
4. Resolución.
5. Seguimiento, cuando corresponda.

El proceso debe reflejar la realidad del negocio.

No se deben inventar garantías o procedimientos que no estén definidos.

---

16. ELEMENTOS DE CONFIANZA

Podrán incluirse únicamente señales reales y verificables, por ejemplo:

- experiencia real;
- certificaciones reales;
- garantías reales;
- horarios reales;
- cobertura real;
- datos de contacto reales;
- reseñas reales cuando el sistema disponga de ellas de forma legítima.

Nunca se deben fabricar testimonios, certificaciones, años de experiencia o garantías.

---

17. DIFERENCIACIÓN

Cada landing debe tener una razón para existir.

La diferenciación puede proceder de:

- intención específica;
- servicio específico;
- información local;
- problema concreto;
- tipo de cliente;
- cobertura;
- datos comerciales;
- información útil propia.

La simple sustitución del nombre de la localidad no constituye diferenciación suficiente.

---

18. FAQ

La landing puede incorporar preguntas frecuentes cuando exista una necesidad real.

Las preguntas deben derivarse de:

- investigación;
- intención;
- preguntas observadas;
- conocimiento real del servicio;
- información comercial disponible.

No deben generarse FAQs artificiales únicamente para introducir keywords.

Las respuestas deben ser verificables.

---

19. CTA

La landing debe tener una acción principal coherente con la intención.

Ejemplos:

- llamar;
- solicitar presupuesto;
- contactar por WhatsApp;
- pedir cita;
- solicitar servicio.

El CTA concreto dependerá del modelo comercial real.

No se debe inventar disponibilidad inmediata ni tiempos de respuesta.

---

20. FOOTER

El footer debe ser global y coherente con el sitio.

Puede incluir:

- servicios;
- navegación;
- localidades estratégicas;
- contacto;
- información legal.

No debe utilizarse como mecanismo indiscriminado para enlazar miles de páginas.

---

21. SEO ON-PAGE

Cada landing deberá disponer de datos estructurados de contenido suficientes para generar, cuando corresponda:

- title;
- meta description;
- H1;
- headings;
- URL canonical;
- enlaces internos;
- datos estructurados cuando proceda;
- atributos relevantes de imágenes.

Estos elementos estarán condicionados por la intención y por las reglas SEO del proyecto.

---

22. ENLAZADO INTERNO

La landing debe poder enlazar hacia páginas relevantes del sitio.

Los enlaces pueden conectar:

- servicio principal;
- subservicios relacionados;
- localidades relevantes;
- páginas superiores;
- contacto.

No deben generarse enlaces automáticamente hacia páginas inexistentes.

Tampoco debe crearse una red artificial de enlaces entre todas las páginas.

---

23. SELECCIÓN DE BLOQUES

No todas las landings necesitan todos los bloques.

Existirán:

BLOQUES OBLIGATORIOS

Elementos mínimos comunes a toda landing.

BLOQUES CONDICIONALES

Se incorporan si existen datos o si la intención los justifica.

BLOQUES OPCIONALES

Se utilizan únicamente cuando aportan valor.

La definición detallada de cada bloque se realizará en:

"proyecto/seo/sistema-bloques.md"

---

24. REGLA DE DATOS

La arquitectura de landing no debe pedir a la IA información que el sistema no posea.

Cada bloque debe indicar qué datos necesita.

Ejemplo:

Bloque: cobertura

Datos necesarios:
- zonas atendidas
- municipio
- cobertura confirmada

Si los datos no existen, el bloque debe:

- omitirse;
- utilizar una versión más general;
- o pasar la oportunidad a validación.

---

25. REGLA CONTRA LA INVENCIÓN

La IA nunca debe inventar:

- direcciones;
- teléfonos;
- precios;
- horarios;
- disponibilidad;
- empresas;
- nombres de técnicos;
- certificaciones;
- testimonios;
- garantías;
- barrios atendidos;
- características locales no verificadas.

La ausencia de información no debe solucionarse inventándola.

---

26. RELACIÓN CON LA URL

La landing recibe una URL ya determinada.

Ejemplo:

"/fontanero/desatascos/marbella/"

La arquitectura de landing debe adaptar el contenido a esa identidad.

No debe cambiar la URL ni crear otra intención.

---

27. RELACIÓN CON EL MODELO DE DATOS

Cada landing deberá construirse a partir de un objeto de datos estructurado.

Como mínimo:

subservicio
localidad
provincia
url
decisión
intención
evidencias
datos_locales
datos_comerciales
bloques_obligatorios
bloques_condicionales
restricciones

El modelo completo se definirá posteriormente en:

"proyecto/seo/modelo-datos.md"

---

28. RELACIÓN CON IA

La IA recibe:

- identidad de la página;
- URL;
- intención;
- datos;
- evidencias;
- bloques;
- restricciones;
- reglas SEO.

La IA genera el contenido dentro de esos límites.

No decide estratégicamente:

- si la página debe existir;
- qué URL debe tener;
- qué localidad debe utilizar;
- qué servicio debe representar.

---

30. REUTILIZACIÓN

Esta arquitectura debe poder utilizarse para:

- fontanería;
- abogados;
- electricistas;
- carpinteros;
- pintores;
- jardineros;
- reformas;
- climatización;
- otros servicios.

La estructura es general.

Los bloques y datos concretos pueden variar por sector.

---

31. ESCALABILIDAD

El sistema debe permitir construir:

- 1 landing;
- 5 landings;
- 50 landings;
- 500 landings;
- o más;

utilizando la misma arquitectura y cambiando únicamente los datos y bloques justificados.

El número de páginas nunca debe ser el objetivo principal.

La calidad y la utilidad tienen prioridad.

OPP-001

OPP-003
OPP-004
OPP-005

URL 1
Datos 1
Bloques 1

URL 2
Datos 2
Bloques 2
Contenido 2

...

La arquitectura será la misma, pero los datos, evidencias, intención y bloques condicionales podrán ser diferentes.

---

34. VALIDACIÓN ANTES DE PUBLICAR

Antes de publicar se deberá comprobar como mínimo:

- URL correcta.
- Servicio correcto.
- Subservicio correcto.
- Localidad correcta.
- H1 correcto.
- Intención correcta.
- Datos locales respaldados.
- Datos comerciales respaldados.
- Bloques obligatorios presentes.
- Contenido no inventado.
- Contenido suficientemente específico.
- Ausencia de duplicación evidente.
- Canonical correcto.
- Enlaces internos válidos.
- CTA correcto.

La validación detallada se definirá posteriormente en:

"proyecto/seo/validacion.md"

---

35. PRINCIPIO DE FALLBACK

Si un bloque necesita datos que no existen, el sistema no debe rellenarlo con contenido inventado.

Debe utilizar uno de estos comportamientos:

1. Omitir el bloque.
2. Utilizar una versión genérica segura.
3. Solicitar información.
4. Marcar la landing para revisión.
